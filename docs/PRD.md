## 1. 文档信息

### 1.1 一句话定位

**一款本地优先、AI 增强的跨平台阅读器：把自己收藏的书读好、读透、读得下去。**

### 1.2 范围声明

| 维度 | 本期结论 |
|---|---|
| 内容来源 | **仅本地文件**。不做书源、不做在线书城、不做内容抓取 |
| 支持格式 | EPUB、TXT、PDF、MOBI/AZW3、CBZ/CBR（分优先级落地，见 §7） |
| 增强能力 | **AI 增强**（4 项）、**TTS 朗读**、**WebDAV 同步** |
| 高性能层 | **可选加速层**：Rust 在既有抽象接口之后做高性能实现，与纯 Dart 实现并存，不适用时**自动回落**（v2.4 变更 B，见 §15.6） |
| 视觉风格 | **玻璃态**（导航层玻璃、内容层不透明，见 §11） |
| 平台 | **五平台**（Android / iOS / Windows / macOS / Linux），**分优先级**（见 §15）。**Web 已放弃**（v2.4 变更 A，见 §15.2） |

### 1.3 本项目的独立性声明（重要）

本项目是**独立立项的全新项目**，产品需求**独立定义、不从任何既有工程继承**。

- 需求层面：不继承任何既有阅读器的功能集合、命名体系、交互形态或数据模型。本项目的需求**只以本文档为准**。
- 实现层面：**允许且鼓励**借鉴成熟开源实现的算法与协议约定（尤其是解析算法、备份格式、同步目录约定），以降低重复造轮子的成本。可参考的代码来源见 §附录 A。
- 判断准则：**「怎么做」可以借鉴，「做什么」必须重新定义。** 任何以「因为某某项目是这么做的」为唯一理由的需求，在本项目中不成立。

## 2. 产品目标与定位

### 2.1 三大支柱

| 支柱 | 一句话 | 对应需求域 |
|---|---|---|
| **读得下去** | 本地书能导入、能排版好、能记住进度、能大字夜读、大书不崩 | 书库 / **书籍详情与元数据** / 阅读内核 / 排版 / 导航 / **阅读统计** |
| **读得透** | 长书、外文书、大部头能借 AI 快速理解与回顾 | AI 增强 |
| **读得方便** | 能听、能在多设备间带着进度走 | TTS / WebDAV |

### 2.2 要解决的问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | 本地藏书格式杂、来源乱，很多阅读器只认 EPUB | 手头有 TXT 网络小说、Kindle 的 AZW3、扫描 PDF、漫画压缩包 |
| 2 | 中文老书编码混乱（GBK、编码声明撒谎），多数阅读器直接乱码 | 需强编码探测与兜底 |
| 3 | 长书读不动：读完一段停一周，回来就想不起剧情 | 需要「前情回顾」这类 AI 能力 |
| 4 | 外文/古籍/专有名词读起来吃力 | 需要划词翻译与释义 |
| 5 | 大部头人物关系复杂 | 需要人物关系与设定梳理 |
| 6 | 通勤/做家务时想听书 | 需要 TTS 朗读 |
| 7 | 手机读到一半，换桌面继续 | 需要进度同步 |
| 8 | 读了不少，却说不清「读得下去」这件事自己坚持得怎么样 | 需要阅读时长、活跃天数与连续阅读天数的客观反馈，而不是凭感觉 |
| 9 | 导入后封面与作者常常空着，得一本本手动补 | 多数格式能从文件内嵌元数据或文件名自动读出封面与作者；缺失时需统一兜底，并标出「书名/作者是书里带的还是从文件名猜的」 |

### 2.3 本期不做（非目标）

以下为**明确排除**，不进入需求池，也不作为「顺手做了」的借口：

- **书源 / 在线书城 / 网络搜索 / 内容抓取 / 在线导入 URL**
  （注：本期不做的原因与实现难度无关，是产品定位选择——本项目只处理用户已有的文件）
- **在线元数据补全**（书籍详情页的「刷新补全 / 换源」、封面规则、第三方封面或书目接口）
  （这也是「书籍详情自动获取封面与作者」的边界：只做**本地文件内嵌元数据 + 文件名推断**，不做任何联网抓取）
- 社交（评论、划线分享、书单）、账号体系、社区
- 商业变现（广告、会员、付费、统计埋点）
- DRM 破解（加密 EPUB/AZW3 一律拒绝并提示）
- 端侧本地大模型推理（AI 统一走云端 API，见 §8）
- 有声书的音频文件管理（TTS 只是把文本读出来，不做音频库）
- 读书笔记的富文本编辑（只做划线 + 纯文本笔记）
- **阅读统计的系统提醒 / 通知推送**、**统计的社交化对比与全站排行**（统计只在 App 内呈现，且只对本机数据做聚合，见 §14.2）
- 跨平台校准 UI（不做「一套设计稿 5 份像素级还原」的追求）
- **把整条阅读链路改写成 Rust**（本期只做 §15.6 的**可选加速层**：Rust 挂在既有抽象之后，与纯 Dart 并存并自动回落；**不做全链路重写、不做端侧性能重写**）

```
   └─────┴────────┴────────┴─────────┴──────┘
      │
⑧ 玻璃态视觉体系（横切：贯穿 ①③④⑩⑪ 的页面外壳）
      │

      │
⑫ Rust 高性能能力层（横切 · 可选加速层）

     未编译 / 平台不支持 / 加载失败时自动回落纯 Dart，上层不感知）
```

**关键排序原则**：③④ 是 ② 的下游（先把书读对，再谈读好）；⑤⑥⑦ 都建立在「书已经能正常打开」之上；
⑩ 是 ②③ 的下游（先有稳定的阅读会话与进度模型，才有可信的时长），**但它的采集内核（`STAT-01/02`）只有数据层、
不依赖任何页面，可以且应当先行落地**，统计页本身不阻塞任何其他分支；
⑪ 是 ① 的直接下游（元数据在导入时一次性解析落盘），**被 ①（书架展示封面/作者）与 ⑩（书籍详情页展示单书统计）消费**，
自身不消费 ②③，因此**可与 ② 并行落地**，不被阅读内核阻塞；
⑧ 只作用于页面外壳，**不进入阅读正文区**；
⑫ 是**实现层的横切替换**，不新增任何用户可见页面：它挂在 ② 的解析抽象之后（§7.1），仅在「纯 Dart 基线超过 §15.6.3 阈值」时才实施（`RUST-06`），因此**排在 M2b / M3 的纯 Dart 基线之后**（见 §17 M3.5），**不阻塞任何主链路**，也不得被当作任何新格式 / 新功能的前置条件。

#### 书籍详情与元数据（META）

> **本域只做「本地文件内嵌元数据 + 文件名推断」**：解析在导入时一次性完成并落盘，详情页只做展示与手动修改，
> **不做任何联网抓取**（在线补全 / 换源 / 封面规则 / 第三方接口一律不做，见 §2.3、§14.2）。
> 因此**不存在把书名/作者/封面发到第三方的行为**——这是本项目的隐私优势（可与 §6.1 `DATA-02`、`AI-09` 对照）。
>
> **格式优先级跟随 §7.2**：EPUB / TXT 的封面与作者提取为 **P0**（见下方 `META-01~07`）；
> PDF / CBZ 封面随 `FMT-01/02` 落 **P1**（`META-10/11`）；MOBI/AZW3 随 `FMT-04` 落 **P2**（`META-12`）。
>
> **与 `LIB-01` 的关系（消除自相矛盾）**：`LIB-01`（P0）要求书架展示**封面 + 作者**，而原 `CNT-07` 的封面提取却是 P1、
> 排在 M2a——这会导致 M1（P0 交付）时书架拿不到真封面与真作者。故本版把 **EPUB / TXT 的封面与作者提取升入 P0**
> （`META-02/03/04/07`）：EPUB 的 OPF 本就在解析、TXT 只是几条正则，**几乎不增加成本**；其余格式仍按其格式优先级顺延。

| 编号 | 需求名 | 描述 | 验收要点 |
|---|---|---|---|
| **META-01** | 元数据统一模型与来源标记 | 定义统一书籍元数据模型 `BookMeta`（**书名 / 作者 / 封面 / 简介**），每个字段**独立携带来源标记**：`metadata`=来自文件内嵌元数据 / `filename`=由文件名推断 / `user`=用户手动编辑 / `none`=缺失。导入解析时一次性写入并落盘，书架与详情页只消费该模型，不感知格式差异（§7.1）。**缺失兜底统一**：书名缺失 → 退回「文件名去扩展名」，仍为空 → 「未命名书籍」；作者缺失 → **统一显示「未知作者」，不得留空字符串**。 | ① 导入 1 本 EPUB + 1 本 TXT，模型内每字段的来源标记与实际一致（EPUB 书名=`metadata`、TXT 书名=`filename`）；② 把某书作者清空后界面显示「未知作者」而非空白；③ 书名与作者都缺失的构造样本不崩溃且两项均有兜底文案；④ 解析单本失败只影响该书，不阻塞书架其余书籍 |

| **META-03** | EPUB 书名与作者提取 | 书名取 OPF `dc:title`；作者取 OPF `dc:creator`，**多作者按稳定顺序整体保留**（不假装切分）；作者为空时按 `META-01` 兜底为「未知作者」，或由文件名解析结果补足。 | ① 含多个 `dc:creator` 的书作者都能显示且顺序稳定；② 有标题无作者的书，作者回退为文件名解析结果；③ 书名/作者均缺时按 `META-01` 兜底 |
| **META-04** | TXT 书名与作者解析（规则链与兜底） | 对**文件名**依序应用、**命中即停**：① 用户自定义规则（若配置）→ ② 内置规则集 → ③ 文件名清洗兜底。内置规则集至少覆盖四类：`《书名》…作者：X`、`《书名》…`、`书名 作者：X`、`书名 by X`。清洗统一去除 `作者xxx` / `xxx 著` 尾巴并收拢多余空白。**兜底判定精确化**：以「书名占位被移除后，作者候选串非空且与原文不同」为保留条件，**不得**用「长度是否相同」这类粗糙判据。 | ① `《三体》作者：刘慈欣.txt` → 书名=三体、作者=刘慈欣；② `活着 by 余华.txt` → 书名=活着、作者=余华；③ `红楼梦.txt`（无作者信息）作者为「未知作者」而非空；④ 作者与书名恰好等长的构造用例**不被误丢弃**；⑤ 解析结果的来源标记为 `filename` |
| **META-05** | 封面存储、格式保真与缩略图 | 封面写入应用私有目录 `covers/`，**保留源字节**并按**真实格式**（JPEG / PNG / WebP…）落盘与命名，**不做强制 JPEG 重编码**（避免透明通道丢失与「后缀名与内容不符」）；同时生成**独立缩略图**供书架列表使用（书架**不**逐本缩放原图）。解码遵循**像素上限**（超限先降采样再解码）与**缓存上限**。 | ① 带透明通道的 PNG 封面导入后透明通道保留、后缀与真实格式一致；② 书架使用缩略图而非原图（对比解码尺寸）；③ 导入一张 5000×7000 大封面，解码不出现内存尖峰（按 §13.2 `NF-M5` 口径）；④ 书架滚 20 本不重复解码同一封面 |
| **META-06** | 封面文件生命周期与孤儿 GC | 封面文件与书籍**同生命周期**：① 手动换封面后删除旧封面文件；② 删除书籍时连带删除其封面文件（含用户自定义封面，见 `LIB-06`）；③ 「清空缓存」时清理 `covers/` 下**不被任何书籍引用**的孤儿文件；④ 封面引用一律用**显式枚举 / 空值**表达，**禁止**魔法字符串。 | ① 连续换 3 次封面后 `covers/` 下只保留当前一张；② 删除一本书后其封面文件消失；③ 手工塞入一个未被引用的 `covers/xxx.jpg`，执行清理后被删除；④ 清理不影响仍被引用的封面；⑤ 全工程搜不到 `"use_default_cover"` 一类魔法字符串 |
| **META-07** | 无封面时的合成封面 | 格式本身无封面（TXT）、或封面提取失败时，按**降级顺序**处理：① 用书名 + 作者**运行时绘制合成封面**（背景取主题色/纯色，书名大字居中、作者小字居中于书名下方，长书名自动换行 / 缩放至不溢出）；② 仍不可用时退回默认占位图。合成结果**按「书名 + 作者 + 主题」缓存**，不重复绘制；三者任一变化时失效重建。 | ① 无封面的 TXT 显示「书名 + 作者」合成封面而非空白；② 超长书名不溢出、不截断到不可读；③ 同一本书重复进入书架不重复绘制（命中缓存）；④ 切换日/夜主题后合成封面重新生成且配色适配 |

## 7. 格式支持矩阵

> 本章是本次扩范围的核心。所有格式最终都要落到「章节列表 + 正文（或图片页）」这两个统一抽象上，
> 上层阅读器只依赖该抽象，不感知格式差异。

### 7.1 统一抽象

```
BookSource（格式解析器）
   ├─ load()            → BookMeta（书名 / 作者 / 封面 / 简介 + 各字段的来源标记）
   ├─ chapters()        → List<Chapter>（标题 + 层级 + 定位信息）
   ├─ content(chapter)  → 段落列表 | 图片页列表
   └─ capabilities()    → 本格式支持哪些能力（图片/脚注/重排/搜索）
```

**关键约束**：`BookSource` 各实现必须**互不感知**，由统一的注册表按格式分发。
阅读器只消费抽象结果，新增格式不得修改阅读器代码。

> **v2.4 补充（Rust 加速层的位置）**：Rust 实现挂在**本抽象之后**，与纯 Dart 实现**并存**（§15.6.1）。
> 注册表按「能力探测结果」选择实现，两份实现的产出必须**等价**（`RUST-02`）；上层**不感知**用的是哪一份（`RUST-01`）。
> 也就是说：Rust 是**替换实现**，不是新能力——本抽象定义的契约仍以纯 Dart 基线为准。

### 7.2 支持矩阵

| 格式 | 优先级 | 解析路径 | 主要风险 | 对应需求 |
|---|---|---|---|---|
| **EPUB 2/3** | **P0** | 纯 Dart 自研：`archive` 解 zip + `xml`/`html` 解析；OPF → nav.xhtml/toc.ncx 双路径目录；正文按块提取 | 脏 XHTML 容错（Dart 的 `html` 包宽容度低于 Jsoup） | RD-01 / CNT-01~06 / `META-02/03` |
| **TXT** | **P0** | 纯 Dart 自研：编码探测 → 正则规则集分章 → 字数切块兜底 | 编码误判（Big5/Shift-JIS 易被当 GBK）；分章规则误判（把卷当章） | RD-02 / `META-04` |
| **PDF** | **P1** | **第三方渲染插件**（渲染页为位图）→ 按固定页数合成伪章节 | 插件选型与五平台覆盖；文字层是否可用于搜索 | FMT-01 / `META-10` |
| **CBZ** | **P1** | 纯 Dart：`archive` 解 zip → 图片页按自然序排列 | 页数极大时的内存与预加载策略 | FMT-02 / `META-11` |
| **CBR** | **P1** | rar 解压需平台能力或 FFI 绑定 | Dart 生态无 rar 支持，可能只能「识别 + 提示」 | FMT-03 / `META-11` |
| **MOBI / AZW3 / AZW** | **P2** | 纯 Dart 自研：PDB 容器 + KF6/KF8 双格式 + Huff/CDIC 解压 | **本期成本最高的单项**；无 Dart 生态可借，需移植算法。**v2.6 补录**：「无 Dart 生态可借」对 **Dart 包生态**成立，但存在**可直译的 Kotlin 参考实现**——567Reader `app/src/main/java/**/lib/mobi/`（33 文件约 1600 行，纯 Kotlin 自研：PDB 容器 / KF6 连续 HTML 流窗口 / KF8 SKEL+FRAG+FDST+INDX / Plain·LZ77·HUFF-CDIC 三解压器），是纯 Dart 原型基线（M2b `FMT-04`）的最短路径 | FMT-04 / `META-12` |

> **v2.4 补充（Rust 档位 3 与本表的关系）**：上表「纯 Dart 自研」为**基线实现**。其中 **EPUB 解压（zip 层）、
> TXT 编码探测与大文件分章、MOBI/AZW3 解压**属 **Rust 档位 3 候选能力**（§15.6.2）；只有纯 Dart 基线实测**超过 §15.6.3 阈值**
> 才在其后挂一份 Rust 加速实现（`RUST-01/02`）。**本表结论不变**——所有格式的功能契约由纯 Dart 基线定义。
>
> **v2.5 补充（同一格式内部的层拆分）**：EPUB 的「**XHTML → 段落（正文抽取层）**」**首版不纳入 Rust**，保持纯 Dart
> （理由：等价性无法成立，见 §15.6.2）。也就是说：**同一种格式可以只把「解压层」Rust 化**——层级边界以
> 「Rust 实际替换掉哪一层」为准，**不以格式名划分**。

### 7.3 格式分发规则

## 8. AI 增强模块

### 8.1 定位

AI 是**阅读的辅助层**，不是产品的核心卖点。判断准则：

> **任何 AI 功能失效时，阅读器必须仍是一个完整的阅读器。**
> AI 入口在未配置时隐藏或禁用，不得出现「因为没配 Key 所以连书都打不开」。

### 8.2 Provider 模型（OpenAI 兼容）

| 配置项 | 说明 |
|---|---|
| `name` | 配置名（如「自建 One-API」「DeepSeek」） |
| `baseUrl` | 兼容 OpenAI 的 base URL（如 `https://api.deepseek.com/v1`） |
| `apiKey` | 密钥（安全存储，见 DATA-02） |
| `model` | 模型名 |
| `customHeaders` | 自定义请求头（部分中转需额外头） |
| `timeout` | 超时（默认 60s） |
| `maxTokens` / `temperature` | 生成参数 |
| `useFor` | 该配置用于哪些功能（对话 / 翻译 / 摘要 / 嵌入） |

**多配置支持**：至少可保存 2 套并分别指定用途（如「摘要用便宜模型、问答用强模型」）。

**TTS 复用**：在线 TTS 若走 OpenAI 兼容的 `audio/speech` 端点，可复用同一 `baseUrl` 与 `apiKey`，
只额外配置 voice / 格式 / 语速。这样用户配一次即可同时获得 AI 与在线朗读能力。

### 8.3 四项功能

| 功能 | 输入 | 输出 | 上下文范围 | 缓存策略 |
|---|---|---|---|---|
| **划词翻译** | 选中文本 + 前后各 1 段 | 译文（流式） | 仅选中文本 + 少量上下文 | 按「文本 hash + 目标语言」缓存 |
| **划词释义/生词** | 选中词/短语 + 所在段落 | 释义 + 语境说明 | 仅所在段落 | 按词 + 段落 hash 缓存 |
| **章节/全书摘要·前情回顾** | 章节全文（超长则分块递进） | 梗概 | 当前章 / 已读章节 | 按「章 id + 内容 hash + 模型」缓存 |
| **跟书问答（RAG）** | 用户问题 | 答案 + 引用位置 | **检索出的相关片段**，非全书 | 向量/关键词索引本地持久化 |
| **人物关系与设定** | 指定进度范围的正文 | 人物清单 + 关系描述 | 可限定「仅已读部分」防剧透 | 按「进度范围 + 内容 hash」缓存 |

> **v2.4 补充（Rust 档位 3 与本模块的关系）**：**RAG / BM25 索引构建**属 Rust 候选能力（§15.6.2 / `RUST-06`），
> 须先有纯 Dart 基线并超过阈值；**AI 的 Provider 配置与网络层不上 Rust**（IO 等待型负载，§15.6.2）。

### 8.4 通用要求（AI-08）

| 要求 | 说明 |
|---|---|
| 流式输出 | 逐字显示，首字节到达即开始渲染 |
| 可取消 | 任何请求都能中断，中断后不留半截缓存 |
| 可重试 | 失败后一键重试；区分「可重试」（超时/5xx）与「不可重试」（401/404） |
| 并发限制 | 同时最多 1~2 个请求，防止连点打爆配额 |
| 结果缓存 | 相同输入命中缓存不重复计费；缓存可清理 |
| 降级 | 未配置 / 不可用时，AI 入口禁用并说明原因，**核心阅读不受影响** |

### 8.5 隐私红线（AI-09）

| 红线 | 要求 |
|---|---|
| **不默认上传整本书** | 任何功能都不得无提示地把全书原文发出 |
| **上下文范围可见** | 每次请求前，UI 明确本次将发送哪些内容（章数 / 字数 / 段落数） |
| **全局开关** | 一个开关关闭所有 AI 功能 |
| **最保守模式** | 提供「仅发送选中文本」模式，此时问答功能明确标注为受限 |
| **答案标注不确定性** | 问答失败（书中无相关信息）必须回答「书中未提及」，**禁止编造** |
| **凭据不外泄** | Key 与密码进安全存储，**不进备份包、不进日志**（DATA-02） |

## 9. TTS 朗读模块

### 9.1 双引擎

| 引擎 | 适用 | 依赖 |

| **系统 TTS** | 默认，零配置、离线可用 | 平台 TTS 插件 |

### 9.2 朗读粒度与高亮

| **平台差异** | 字级高亮回调在 iOS 上支持不完整，**必须**能降级到段落级，不得因缺字级回调而功能失效；**Linux 的系统 TTS 覆盖不确定**（依赖发行版是否安装语音后端，见 §15.3），缺失时必须给出「本机未安装语音引擎」的中文提示，**不得静默失败** |

### 9.3 后台与系统集成

| 能力 | 要求 |
|---|---|
| 后台播放 | 锁屏 / 切后台继续朗读 |

| 锁屏与耳机键 | 媒体键可用 |
| 音频焦点 | 丢失自动暂停，瞬失恢复后自动继续 |
| 来电 | 来电暂停，挂断后按设置恢复 |
| 熄屏 | 朗读期间保持唤醒 |
| 拔耳机 | 自动暂停 |

### 9.4 与阅读进度联动

朗读持续写入阅读进度（同一套 `章节索引 + 章内位置` 模型），停止后下次打开回到该位置。
**朗读不得产生第二套进度模型**——否则「读到一半停下来翻页继续读」会导致进度打架。

## 10. WebDAV 同步模块

### 10.1 同步范围

| 类别 | 内容 | 同步方式 |
|---|---|---|
| 阅读进度 | 每本书的章节索引 + 章内位置 + 时间戳 | **增量**，单书单文件 |
| 书签 / 笔记 | 按条目 | 增量，按条目合并 |
| 阅读设置 | 字号/行距/边距/主题/字体/亮度 | 增量，取最近修改 |
| 书库索引 | 书名/作者/格式/路径/导入时间/**元数据来源标记与封面引用**（封面图像文件本身随「书籍文件」开关，见下） | 增量 |
| AI 缓存 | 摘要 / 人物梳理结果 | 可选（体积大，默认关） |
| **阅读统计** | 会话级明细（`id` / `book_id` / `day_key` / `started_at` / `duration`） | **可选开关，默认开启**；按 `id` **并集**合并（见 `STAT-08`） |
| **书籍文件** | 书籍本身**及其封面文件** | **可选开关，默认关闭** |
| **API Key / WebDAV 密码** | — | **永不同步**（红线） |

### 10.2 冲突策略：「取更新」

判定顺序（必须按此顺序，不可简化）：

1. 比较**远端文件修改时间**与本地记录的同步时间，远端更旧 → 直接跳过
2. 比较**章节索引**，更大者胜
3. 索引相同则比较**章内位置**，更靠后者胜
4. 完全相同时不写入，仅更新时间戳

> 设计理由：单纯比时间戳会在「设备时钟不准」时丢失进度；纯比位置又无法处理「回退重读」。
> 两者串联才既能防丢、又能防回退覆盖。

> **阅读统计不适用本节策略**：统计数据是「可累加的事实」而非「可回退的状态」，用「取更新」会把另一台设备
> 上的时长直接丢掉。因此统计按**会话 `id` 并集**合并（`STAT-08`），保证幂等且可累加。这也是本项目
> 必须保留**会话级明细**、而不按天聚合成一行的直接原因。

### 10.3 目录约定

```
{webdavUrl}/{dir}/                    # dir 默认 "mreader"
├── backup-{yyyy-MM-dd}-{device}.zip  # 全量备份包
├── bookProgress/{书名}_{作者}.json    # 单书进度（增量）
├── stats/                            # 阅读统计（会话级明细按月分片，可关闭）
├── books/                            # 书籍文件（可选开关）
└── assets/                           # 背景图等（可选）
```

**全量备份包内容**（至少包含，且**不含**凭据）：

```

progress/          全部书籍进度
bookmark.json      书签
note.json          笔记
settings.json      阅读设置
stats/             阅读统计（会话级明细）
aiCache/           AI 摘要与人物梳理缓存（可选）
meta.json          版本号、导出时间、设备名、包内文件清单
```

> **兼容性说明**：目录与文件命名有意贴近现有开源阅读器生态的约定，以降低互操作成本。
> 但**本项目的数据模型独立定义**，不承诺与任何既有实现的双向兼容；若需兼容，应作为独立需求提出。

### 10.4 触发时机

| 时机 | 动作 |
|---|---|
| App 启动 | 拉取进度（仅拉进度，不拉书籍） |
| 退出阅读页 | 上报当前书进度 |
| 退出 App | 上报全部变更 + 判断是否到全量备份间隔 |
| 手动 | 设置页提供「立即同步」「立即备份」「从云端恢复」 |

**不做**：系统级定时任务（AlarmManager / WorkManager 类）——收益低、权限成本高、各平台差异大。
自动备份只在用户实际使用 App 时触发。

### 10.5 同步失败可见（SYNC-07）

任何同步失败必须**可见**：给出失败条目清单与原因（401 / 404 / 网络不可达 / 磁盘满），
并提供手动重试。**禁止静默失败**——静默失败会让用户误以为数据已备份。

### 11.2 玻璃 / 不透明 分界（核心设计决策）

**这是本模块最重要的一条规则，任何页面设计都必须遵循：**

| 层级 | 具体位置 | 处理 |
|---|---|---|
| **导航层** | 应用顶栏、底部标签栏、工具栏 | ✅ **玻璃** |
| **浮层** | 对话框、底部弹窗、菜单、Popover | ✅ **玻璃** |
| **控制组件** | 设置页内的按钮、滑块、分段控件、开关、输入框 | ✅ **玻璃** |
| **卡片容器** | 设置页的分组卡片、AI 面板 | ✅ **玻璃** |
| **内容层** | 书架列表行、目录列表行、搜索结果行、生词本行、**统计排行列表行与统计图表**、**书籍详情页的封面区与简介文本区** | ❌ **不透明** |
| **阅读页正文** | 正文区、图片区、漫画页 | ❌ **不透明**（红线） |

**理由（三重）**：
1. 该组件库的官方设计哲学即为「导航层用玻璃、内容层保持不透明」，逆着用会得到糊成一团的界面；
2. 长文阅读对背景对比度与稳定性极敏感，正文区透出背景会导致阅读疲劳；
3. `premium` 质量**禁止放进 `ListView` / `CustomScrollView`**，放进滚动区会渲染异常——
   书架和目录都是滚动列表，天然只能用 `standard` 或 `minimal`。

### 11.3 质量档位策略

| 场景 | 档位 | 说明 |
|---|---|---|
| 固定顶栏 / 底栏 | `premium` | `GlassScaffold` 会自动把导航栏提升为 premium（经 `GlassIsolationScope`） |
| 可滚动区域内的玻璃 | `standard` | 默认档位，95% 场景适用 |
| 低端设备 / 密集玻璃列表 | `minimal` | 无着色器开销，滚动时零 shader 调用 |
| 用户「降低视觉特效」开关 | 强制 `minimal` | 给性能兜底，且能验证「关掉特效 UI 仍完整」 |

**P0 阶段固定用 `standard`**，不使用 `adaptiveQuality`（该能力标记为 `@experimental`，
首次启动要跑约 3 秒基准测试，且若不持久化 `initialQuality` 每次冷启动都会重现降级窗口）。
待 P1 再评估引入。

### 11.4 已知限制与应对

| 限制 | 应对 |
|---|---|
| **`MaterialApp` 祖先要求**：库自身无 `Material` 祖先，在 `MaterialApp` 下文本会显示黄色双下划线 | 在 `MaterialApp.builder` 中包一层 `Material(type: MaterialType.transparency)` |
| **`premium` 不可放进 `ListView`/`CustomScrollView`** | 见 §11.2 分界规则；滚动区一律 `standard` |
| **玻璃控件不可嵌套**（`GlassCard` 内不得再放 `GlassButton` 等） | 代码评审红线；`GlassCard` 内只放不透明内容 |
| **`cupertino_icons` 为强制依赖** | 保留该依赖，不得从 `pubspec.yaml` 移除（否则玻璃图标显示为 `?`） |
| **`GlassScaffold.backgroundColor` 双重角色**（实体背景色 + 滚动边缘渐隐叠加色） | 提供 `background:` 时需注意仅影响边缘渐隐，背景需另行处理 |
| **`GlassPerformanceMonitor` 连续 60 帧超预算会抛 `FlutterError`** | release 下自动零开销禁用；debug 下若触发说明特效确实过重，应降档 |
| **Windows 使用 Impeller ANGLE 需 Flutter 3.47+** | ⚠️ **2026-09-28 修正**：本项目原为 3.44.9（**不满足**该门槛），**已于 2026-09-24 升到 3.47.5**（见 §11.1 与 §16 `Q3`）→ **原「Windows 只能走 Skia 轻量 shader 路径」的前提不再成立**。但**库自身仍把 Windows / Linux 静态封顶 `standard`**（见本表下一条，1.7.0 已复核）→ Windows 观感仍可能与 Android 不同，**只是原因不再是「没有 Impeller ANGLE」**，而是库的既定策略。验收仍**按平台分别判定、不要求像素级一致**；**实际观感差异须在 Windows 上重新实测后才能下结论** |
| **无障碍近似**：Flutter 未暴露独立 `reduceTransparency`，库用 Increase Contrast 近似 | 记录为已知差异，不额外处理 |
| **`GlassTabBar.minimizable` 需自行处理多尺寸**（iPad 不最小化） | 由本项目的自适应规则接管 |

### 11.5 性能预算（UI-06）

|---|---|

### 12.2 关键流程

**F1 导入多格式书籍**
```
书架「导入」→ 系统文件选择器（可多选，过滤器含全部支持格式）
  → 逐个：嗅探格式 → 判加密 → 判重 → 复制进私有目录 → 解析元数据与目录
  → 进度面板展示「成功 N / 失败 M / 进行中」
  → 失败项列出文件名 + 原因，可单独重试
  → 完成后书架刷新，新书置顶（按导入时间）
```

**F2 打开书与恢复进度**
```
点书架项 → 读索引取进度（章节 + 章内比例）
  → 后台 isolate 解析目标章节 → 渲染
  → 定位到目标段落（±1 屏内）
  → 顶部轻提示「已恢复上次阅读位置」（可关闭，仅一次）
```

**F3 改字号不跳走（TYP-02）**
```
用户调字号 → 记录「当前屏幕顶部所在段落索引 + 该段内偏移比例」
  → 重排（内容高度变化）
  → 用新的段落布局反查该段落的新位置 → 滚动到该处
  → 校验：调整后该段仍在可视区内
```

**F4 划词 AI 处理**
```
长按选中文本 → 浮出 GlassMenu（翻译 / 释义 / 存生词本 / 提问）
  → 显示将发送的上下文范围（选中文本 + N 字上下文）
  → 流式输出到 GlassSheet
  → 可取消 / 可重试 / 可复制 / 可存生词本
```

**F5 跟书问答（RAG）**
```
AI 面板 → 输入问题
  → 本地索引检索 Top-K 相关片段（不发送全书）
  → 显示「将发送 K 个片段，共 X 字」
  → 流式生成答案，附引用条目
  → 点引用 → 关闭面板并跳转到原文位置
  → 书中无相关信息时回答「书中未提及」
```

**F6 朗读**
```
控制条点「朗读」→ 从当前段开始
  → 高亮当前段 + 自动滚入可视区
  → 每段读完写入进度
  → 段末自动下一段，章末自动下一章
  → 锁屏/切后台 → 通知栏与媒体键接管
  → 停止/暂停 → 落盘进度
```

**F7 同步进度（冲突取更新）**
```
启动 → 拉取远端 bookProgress/
  → 逐本：远端 mtime <= 本地 syncTime ? 跳过
        : 远端章节索引 > 本地 ? 覆盖
        : 索引相同且远端章内位置更靠后 ? 覆盖
        : 不写入，仅更新时间戳
  → 失败项汇总提示，可重试
```

**F8 阅读计时与落库（STAT-01 / STAT-02）**
```
进入阅读页 → Stopwatch.start() + 记录 started_at（毫秒）
  → 翻页 / 交互 → 刷新「最后活跃时刻」
  → 连续 N 分钟无翻页且无交互（N 默认 3，见 §16 Q12）→ 暂停计时，暂停期间不计入时长
  → 恢复交互 → 继续计时（同一会话，非新会话）
  → 退出阅读页 / App 离开前台 → 停止计时
  → duration <= 0 → 直接丢弃，不写库（红线）
  → 会话跨 0 点 → 按实际秒数拆成 2 条，各带自己的 day_key
  → 原子写入 stats/session-{yyyy-MM}.json（只重写当月分片）
  → 切后台后回到前台 → 起一个新的会话（新 id、新 started_at）
```

> **与进度写入的关系**：计时落库与进度持久化是**两条独立的写入路径**——进度仍按 `RD-04` 的
> 「章节索引 + 章内位置」模型写在书本身上，统计只写 `stats/`。二者互不依赖，任何一方失败不影响另一方。

**F9 从书架进入书籍详情并编辑元数据（META-08 / META-09）**
```
书架点一本书 → 进入书籍详情页（覆盖 1，顶栏玻璃 / 内容层不透明）
  → 读 BookMeta：封面 + 书名 + 作者 + 来源标记 + 简介 + 进度
  → 封面：点 = 看大图；换 = 从本地选图（来源标记置 user，旧文件按 META-06 删除）
  → 编辑书名 / 作者 / 简介 → 保存（来源标记置 user，不被重新解析覆盖）
  → 点「恢复自动值」→ 回到 metadata / filename 结果，来源标记还原
  → 底部：加入 / 移出书架、继续阅读
  → 单书统计入口 → STAT-09
```

> **为什么解析在导入时一次性完成**：详见 `META-01`。详情页只读已落盘的 `BookMeta`，**不做联网补全**
> （在线刷新 / 换源 / 封面规则一律不做，见 §2.3），因此进入详情页不发任何网络请求（隐私优势，US-64）。

### 13.1 性能（NF-P）

| 编号 | 目标 | 验收方式 |

| NF-P6 | AI 首字节延迟 ≤ 3s（取决于服务商，仅记失败率） | 统计超时率 |
| NF-P7 | 统计落库不阻塞阅读：单次会话写入（重写当月分片）≤ 50ms，且不产生可感知掉帧 | 本机实测（Android 主力机） |

> 统一写在 §15.6.3（对应 `RUST-06`），且判定方向相反——**超过**阈值才上 Rust。

### 13.2 内存（NF-M）

| 编号 | 目标 |
|---|---|
| NF-M1 | 打开书后**稳态**内存不含非章节资源（图片/CSS/字体字节被释放） |
| NF-M2 | 图片解码有缓存上限，连滚 50 张不单调增长 |
| NF-M3 | 反复打开关闭同一本书 5 次，内存不单调增长 |
| NF-M4 | 朗读与 AI 并行时不出现内存尖峰导致的重启 |
| NF-M5 | 封面与缩略图解码受**像素上限**约束：导入大尺寸封面（如 3000×4000 以上）时先降采样再解码，书架滚动不因逐本解码封面原图而产生内存尖峰（对应 `META-05`） |

> **口径说明**：内存必须分两个口径测量——**峰值** ≈ 原始文件字节 + 解压后全部字节（OOM 主因）；
> **稳态** ≈ 仅当前持有内容的字节。只报一个数字会掩盖真实问题。

### 13.3 兼容性（NF-C）

| 编号 | 目标 |

| NF-C1 | 现有 14 本脏书 fixture 回归测试全部通过 |

| NF-C6 | 玻璃态效果在 Android 与 Windows 上分别验收，接受视觉差异（见 §11.4） |
| NF-C7 | 统计 `day_key` 一律按**本地时区**计算；修改设备时区或跨时区后，已落盘的会话不得被重复计数或凭空消失（时区只影响此后新记录的 `day_key` 归属） |
| NF-C8 | **平台范围为五平台**（Android / iOS / Windows / macOS / Linux，Web 已放弃，见 §15.2）；**不得宣称五平台功能等价**——各平台差异须按 §15.3 的诚实降级表**如实标注**，验收**按平台分别判定**（典型：Linux 的系统 TTS 与凭据安全存储覆盖不确定、**Windows 玻璃被库静态封顶 `standard`**——§11.4；原注「Windows 走 Skia 轻量路径」的前提已随 Flutter 3.47.5 升级失效，见 §11.1） |

### 13.4 数据安全（NF-D）

| 编号 | 目标 |
|---|---|
| NF-D1 | 所有本地数据**原子写入**（临时文件 + rename） |
| NF-D2 | 读取失败时回退上一份有效副本 |
| NF-D3 | 凭据进系统安全存储，不进备份包、不进日志 |
| NF-D4 | 远端同步采用 HTTPS/WSS，拒绝明文凭据传输 |
| NF-D5 | 提供「清空所有本地数据」入口，且需二次确认 |
| NF-D6 | 阅读统计记录同样受原子写入保护；「清空统计数据」为**独立入口**（二次确认），执行后不得影响书架、进度、书签、笔记与设置 |
| NF-D7 | 封面文件与书籍**同生命周期**：换封面、删书（`LIB-06`）、清缓存时均清理对应 / 孤儿封面文件，长期使用不累积孤儿文件；封面引用不用魔法字符串表达（对应 `META-06`） |
| NF-D8 | **Rust 加速层只出现在只读链路**（解压 / 解析 / 检索 / 索引构建），**不参与任何持久化写入**；因此其加载失败或 panic **不可能损坏用户数据**，且必须回落纯 Dart（`RUST-01` / `RUST-04`） |

### 13.5 无障碍（NF-A）

| 编号 | 目标 |
|---|---|
| NF-A1 | 尊重系统「减少动态效果」 |
| NF-A2 | 玻璃控件遵循库的无障碍桥接；提供「降低视觉特效」开关作为兜底 |
| NF-A3 | 所有图标按钮有语义标签 |

## 15. 平台与依赖策略

### 15.1 架构约束变更（本次最重要的一条）

| 项 | v1.0（旧） | **v2.0（本版）** |
|---|---|---|
| 平台特定 API | **零**，`lib/` 内无 `dart:io`，五平台同一份代码 | **解除**。见下方说明 |
| 跨平台一致性 | 五平台功能等价 | **分优先级**，接受平台间功能与视觉差异 |

**为什么必须解除**：

| 新增需求 | 为什么纯 Dart 做不到 |
|---|---|
| 多格式解析（PDF） | 任何 PDF 渲染方案都需要平台能力或原生绑定 |
| TTS 朗读 | 系统 TTS 是平台能力；后台播放需前台服务 + 媒体会话 |
| 书架 / 进度 / 设置持久化 | 需要应用私有目录定位（依赖 `path_provider` 取目录 + `dart:io` 读写；见 §15.4） |
| 凭据安全存储 | 需系统密钥库（Keystore / Keychain / 桌面密钥库） |
| CBZ/CBR | CBR 的 rar 解压 Dart 生态无支持 |

**解除的代价（必须承认）**：
- 「一份代码跑五平台」的承诺失效，需要在各平台分别验证；
- 依赖数量增加，构建与升级成本上升；
- 五平台内部仍存在能力缺口：典型是 **Linux 的系统 TTS 与凭据安全存储覆盖不确定**（见 §15.3 诚实降级表）。

**控制措施**：所有平台能力一律经**抽象接口**注入（如**应用路径**、存储、TTS、凭据、PDF 渲染），
`lib/` 内只依赖接口；平台实现下沉到独立的平台层目录。这样：
① 核心解析链路仍可纯 Dart 单测；② 某平台缺实现时明确降级而非崩溃；
③ 新增平台只需补实现，不改上层。

### 15.2 平台优先级

| 优先级 | 平台 | 判定 |
|---|---|---|
| **P0** | **Android** | 主力设备，全部功能必须可用 |
| **P0** | **Windows** | 次要设备，全部功能必须可用（PDF/TTS 需确认插件覆盖） |
| P1 | iOS / macOS | 编译通过且核心阅读可用；系统 TTS 与后台播放需验证 |
| P2 | Linux | 尽力而为。Linux 明确允许降级（见 §15.3） |

> **v2.4 平台收敛（变更 A）**：平台范围由六平台收敛为**五平台**——**Web 被整体放弃**（不再是「降级保留」）。
> 触发原因：本次引入 Rust 高性能层后，若保留 Web 就必须额外维护一套 **Rust→WASM 编译链**与 `wasm-bindgen`
> 的兼容性风险；而 Web 原本只是 P2「尽力而为」档，投入产出不成比例，故负责人选择直接砍掉。
> **连带影响**：原 §15.3「Web 平台的诚实降级」已改写为「五平台内的诚实降级」；根目录 `web/` 的清理属**独立工程动作**
> （见 §16 `Q23`），不在本文档需求编号内。**v2.5 修正**：本仓库实测**不存在 `lib/web/`**（只有根目录 `web/`），
> 原措辞「`lib/web/` 与 `web/` 等工程目录」已更正。

> 参考实现中 `PdfRenderer` 是 Android 专有、`libarchive` 是 C 层绑定，
> 这类能力在 Flutter 侧必须重新选型，**不能假设「Android 能跑所以别的也能跑」**。

### 15.3 五平台内的诚实降级（v2.4 改写）

> **本节由原「Web 平台的诚实降级」改写而来**：Web 已整体放弃（见 §15.2），原节的存在意义消失。
> 但「不得宣称平台等价」这条红线的**精神必须保留**——平台数从六减到五，**不等于五平台之间就是等价的**。
> 逐平台等价声明：**Android / Windows 为 P0，必须全功能可用；iOS / macOS 为 P1，核心阅读可用；Linux 为 P2，尽力而为。**

| 能力 | 平台 | 结论 |
|---|---|---|
| 系统 TTS | **Linux** | 覆盖不确定：依赖发行版是否安装语音后端（如 speech-dispatcher / espeak-ng）。**必须给出「本机未安装语音引擎」的中文提示，而非静默失败** |
| 后台朗读与媒体键 | Linux / macOS | 前后台音频会话与媒体键在桌面端覆盖不齐，**允许降级为「仅前台朗读」（负责人已确认，v2.6）**；`TTS-03` 的锁屏控制在移动端仍是硬要求，不受影响 |
| 凭据安全存储 | Linux | 依赖桌面密钥库（libsecret / kwallet）是否可用；不可用时按 `DATA-02` **明确标注为「明文存储」并告知用户** |
| PDF 渲染 | 全平台 | 依赖第三方插件选型（§16 `Q4`）；**iOS / Linux 不支持时允许退化为「识别 + 提示」（负责人已确认，v2.6）**，**不得崩溃** |
| 玻璃态视觉 | Windows | **被库静态封顶 `standard`**（§11.4；1.7.0 已复核）——**按平台分别判定，不要求像素级一致**。⚠️ 原措辞「走 Skia 轻量 shader 路径，视觉弱于 Android」的**前提已随 Flutter 3.47.5 升级失效**（见 §11.1）；实际观感差异**须在 Windows 上重新实测**，本表暂不改判定结论 |
| 中文显示 | Linux | 依赖系统 CJK 字体，缺字体时按 `NF-C3` 提示安装，**不内嵌字体** |
| 排版与阅读内核 | 五平台 | **不受影响**：这一层始终是纯 Dart，平台差异不进入正文渲染链路 |

**红线（原措辞的等价改写）**：**不得在文档或 UI 上宣称五平台功能等价。** 任一平台缺失能力时，必须按上表
如实标注降级原因，**禁止静默失败、禁止用「已支持」覆盖「部分支持」**。

| 渲染后端 | Flutter Impeller | 玻璃着色器性能依赖 Impeller；**Windows 需 Flutter 3.47+ 才有 ANGLE 路径——本项目已于 2026-09-24 升到 3.47.5，该条件已满足**（原注「本项目 3.44.9 只能走 Skia 轻量路径」随之作废）。**Impeller 默认状态已核实**（2026-09-28，读本机 SDK 源码）：Android 由 `flutter_tools/lib/src/project.dart` 的 `_impellerEnabledByDefault = true` **默认启用**（`runner/flutter_command.dart` 中「Android 上 Impeller 可用但非默认」的帮助文本**已过时**，与同 SDK 代码矛盾）；iOS 默认；着色器 AOT 预编译 → 无 Skia 时代的 shader 编译 jank |
| **Rust 加速层（可选，v2.4 新增）** | `flutter_rust_bridge` **锁定 2.13.0**（不写区间）+ Rust 工具链（`rustup` / `cargo` + 各平台 target） | **codegen 版本必须与 `flutter_rust_bridge` 运行时包版本严格一致**（否则生成物与运行时耦合断裂）；本机已装 `flutter_rust_bridge_codegen` 实测为 **2.12.0**，实施时需先升级到 **2.13.0**；FRB 2.13.0 的 MSRV 为 `rust-version = "1.70.0"` ≪ 本机 `rustc 1.89.0`（**余量极大**）。**codegen 豁免边界见 §15.5.1**；构建集成走 `Cargokit`（Gradle / CMake / CocoaPods），**与 Flutter 版本存在已知耦合**（Flutter ≥ 3.32 曾需特定 commit 才能匹配，见 §15.6.5）；**未安装 Rust 工具链时 `flutter build` / `flutter test` 必须仍能通过（自动回落纯 Dart）**（`RUST-07`） |

> ✅ **版本对齐风险（2026-09-28 重判：已消除）**：在 Windows 获得 Impeller ANGLE 渲染路径需把 Flutter 升到 **≥ 3.47**。
> 本项目**已于 2026-09-24 升到 3.47.5**（由 `Q4` PDF 选型链推动，非按 `Q3` 正式立项——见 §16 `Q3` 的改写），
> 因此**「Windows 玻璃只能走 Skia 轻量路径」这一结论不再成立**。
> ⚠️ 但 Windows 观感**仍可能**与 Android 不同——**原因已转为库自身的平台封顶**（`_shouldSkipPremiumPreload()` 对
> `windows` / `linux` 返回 `true`，见 §11.4 末条）；实际差异**须实测**，**不得据本节就宣称「两平台视觉等价」**。

### 15.5 状态管理约束

| 项 | 约定 |
|---|---|
| **允许** | `StatefulWidget` + `setState`；纯 Dart 的数据层与服务层（不依赖任何 UI 框架） |
| **禁止** | Riverpod / Provider / Freezed / 其他状态管理库；用 `build_runner` 生成**业务数据类**（`freezed` / `json_serializable` 等）。**唯一豁免 = §15.5.1 的 FFI 绑定层 codegen** |
| **理由** | ① 各页面的状态量都很小（几个开关 + 一个列表），引入状态管理库的收益不抵学习与调试成本；② 代码生成会引入「生成物与源码不同步」的隐患，在 CI 与 IDE 里各多一层噪音；③ `setState` 是 Flutter 内置能力，**不增加任何依赖**，与 §15.1「核心链路可纯 Dart 单测」的方向一致 |
| **落地要求** | 需要跨页面共享的状态（书库索引、阅读设置、同步配置、**统计聚合结果**）放**进程内单例服务 + 监听回调**：页面在 `initState` 订阅、`dispose` 退订并触发 `setState`；不引入 `InheritedWidget` 之外的共享机制 |
| **验收** | `pubspec.yaml` 与 `lib/` 内搜不到上述库的依赖与导入；**参考实现（`QReader`）的统计模块用的是 Riverpod，移植过来必须落到 `setState`**（对应 `STAT-16`、`STAT-01`） |

> **补充说明**：统计页的「周期切换」「卡片显隐与排序」「图表分段」都是**单页面内的局部状态**，
> 用 `setState` 承载即可；只有「已聚合的时长数据」值得放进单例服务缓存，避免每次切周期都重算。

#### 15.5.1 codegen 豁免条款（v2.4 新增，与 `RUST-*` 配套）

本节前文「禁止代码生成」与 `flutter_rust_bridge`（FRB）的 codegen **存在直接冲突**。
本版给出**显式豁免**并划定边界，**不靠「反正不是 build_runner」含糊过去**：

**查证事实**：
- FRB 的 CLI 是**独立命令** `flutter_rust_bridge_codegen generate`，**不是** `build_runner`；
- 但其参数表里有 `--no-build-runner`，说明**默认在检测到需要时会调用 `build_runner`**。

| 项 | 结论 |
|---|---|
| **豁免范围** | **仅**由 FRB 工具生成的 **FFI 绑定层**：Rust 侧 `frb_generated.rs` / Dart 侧 `frb_generated.dart` 及同批桥接文件。该层是「语言间的机械映射」，不是业务模型 |
| **不在豁免范围** | 用 `build_runner` 生成**业务数据类**（`freezed` / `json_serializable` / 代码生成式 DI 等）——**依然禁止**；Riverpod / Provider 等状态管理库**依然全线禁止**（§15.5 主体不变） |
| **生成物入库（硬要求）** | FRB 生成的 Dart 桥接代码**必须提交进版本库**；日常开发与 CI **不得依赖运行时生成**——即新人 clone 后**不跑 codegen** 就能 `flutter test` / `flutter build` |
| **触发频率约束** | 只有 **Rust 接口签名变更**时才允许重跑 `flutter_rust_bridge_codegen generate`；生成物变更必须与 Rust 侧改动在**同一个提交**，杜绝「生成物与源码不同步」 |
| **验收** | ① `pubspec.yaml` 与 `lib/` 内搜不到 `freezed` / `json_serializable` / `riverpod` / `provider`；② 生成的桥接文件在版本库中可见（未被 `.gitignore`）；③ 全工程不存在「克隆后必须先跑 build_runner 才能编译」的说明 |

### 15.6 Rust 高性能能力层（v2.4 新增 · 变更 B）

> 本节记录**已由项目负责人拍板的四项前提**（定位 / 范围 / 平台 / 门槛），**方向不再讨论**；
> 本节只负责把「定位、范围、门槛、边界、推翻记录、构建代价」写清楚，防止后续被误改。
>
> **口径分工（v2.5 补录）**：**功能契约与门槛以本文档为准**；**技术实现细节以 `docs/architecture-rust-integration.md`
> （架构师产物）为准**。两者冲突时，**功能契约以本文档为准**。该架构文档含 §15.6.2 候选拆分的核实依据、
> §15.6.3 阈值的测量协议、§15.6.4 的 crate 核实、§15.6.5 的构建机制等实现级说明——**这些细节本文档不重复维护**，
> 只保留结论与门槛。

#### 15.6.1 定位：可选加速层，不是重写

| 前提 | 约定 |
|---|---|
| **定位** | Rust 在**既有抽象接口之后**做「高性能实现」（§7.1 `BookSource`、§15.1 平台能力抽象）。它与纯 Dart 实现**并存**，不是替代 |
| **回落** | Rust 未编译 / 平台不支持 / 运行时加载失败 → **自动回落纯 Dart 实现**，**不阻塞主链路、不崩溃**（`RUST-01`） |
| **上层无感** | UI 与业务逻辑**完全不感知**用的是哪一份实现；同一输入下两份实现产出必须**等价**（`RUST-02`）。**唯一例外（v2.6 拍板）**：设置页的加速参数开关（`RUST-10`）是**唯一的显式干预点**——开关经配置值传入加速能力注册表生效，业务 / UI 层不因此新增「是否为 Rust」的分支判断 |
| **纯 Dart 长期保留** | 三条理由：① 未安装 Rust 工具链的环境仍要能跑 `flutter test`；② 它是**性能基线与对照**（阈值判定的基准）；③ 它是**回滚路径**（Rust 线出问题时不必回退版本） |
| **平台范围** | **五平台全部接入**（Android / iOS / Windows / macOS / Linux）。**Web 已整体放弃**（§15.2），因此**不存在 Rust→WASM 编译链**，也就不存在 `wasm-bindgen` 兼容性风险——这正是放弃 Web 的直接收益 |
| **只读链路** | Rust 只出现在**只读路径**（解压 / 解析 / 检索 / 索引构建），**不参与任何持久化写入**（§13.4 `NF-D8`） |

#### 15.6.2 范围：档位 3 · 检索 + 解析

**纳入 Rust 的候选能力（共 6 项；其中 2a / 2b 为 v2.5 由「EPUB 解压与 XHTML 解析」拆分所得）**：

| # | 候选能力 | 对应既有需求 | 为什么 CPU 密集 |
|---|---|---|---|
| 1 | **MOBI / AZW3 解压**（PDB 容器 + KF6/KF8 + Huff/CDIC 解压） | `FMT-04` / `META-12` | Huff/CDIC 是**位级解压算法**，§7.2 原文即写着「**无 Dart 生态可借，需移植算法**」——这是本项目唯一（也是最强）的 Rust 理由。**v2.6 补录**：参考实现的 Kotlin 版含 HTML 清洗层——本项目的清洗层**保持 Dart**（与候选 2b 同一模式），不跨 FFI 直译 |
| 2a | **EPUB 解压（zip 层）** | `RD-01` / `CNT-01~05` | zip 解压 + 条目调度，输出「各章原始字节」（正文抽取层的**输入**）；属 IO / 解压型负载，**是否值得上 Rust 必须靠实测阈值决定**（见 §15.6.4） |
| 2b | **XHTML → 段落（正文抽取层）** | `RD-01` / `CNT-02/03/05` | 宽松 HTML 解析 + 块级切段 + 空白折叠；**首版明确不纳入 Rust**——Dart 侧正文由 `package:html` 产出，其切段行为是该包**特定实现的隐式行为**，Rust（`html5ever` / `lol_html`）几乎不可能逐字节复现，会直接使 `RUST-02` 的 L2 等价性**不可验收**（见下方说明） |
| 3 | **TXT 编码探测与大文件分章** | `RD-02` / `NF-C4` | 大文件多次探测 + 正则规则集择优，属可度量的 CPU 时间 |
| 4 | **全书搜索** | `CNT-06` | 全书逐章扫描 + 上下文片段提取；`CNT-06` 已要求「后台 isolate 执行、可取消」（`RUST-05`） |
| 5 | **RAG / BM25 索引构建** | §8 AI 跟书问答（`AI-06`） | 全书倒排索引构建与打分，是本组中计算量最大的一项 |

> **为什么把「EPUB 解压」与「XHTML → 段落」拆成两项（v2.5）**：v2.4 把两者合成「EPUB 解压与 XHTML 解析」并按**一项**阈值处理，
> 会形成**死结**——若因「解析慢」触发阈值，就必须把这一项 Rust 化；但其中的**正文抽取层（L2）** Rust 化后**无法满足
> `RUST-02` 的等价性**：Dart 侧正文块由 `package:html` 产出，其「块级标签切段 + 空白折叠 + 标题剥离」是该包的
> 具体实现细节，Rust 用 `html5ever` / `lol_html` **几乎不可能**逐字节复现。于是这条需求**既不能验收通过，也不能说它没做**。
>
> **拆分后的三条处置（写死）**：
> 1. **首版 Rust 只替换解压层（L1）**：输出「各章原始字节」，正文抽取仍由纯 Dart 完成 → **L2 天然等价**（同一份 Dart 代码），
>    等价性只需比 L1 与「每章原始字节摘要」；
> 2. **触发判定以合计为准（v2.6 修正，架构师方案 A）**：2a + 2b 合计超过阈值才触发（§15.6.3），**分层值仅作归因与优先级指引**；等价性**只在「Rust 实际替换的那一层」比对**；
> 3. **2b 将来若要 Rust 化，前置条件 = 先把切段规则规格化**（把 `package:html` 的隐式行为写成**显式规则**并用 fixture 固化），
>    **且必须计入合计口径过一次阈值**（分层值仅作归因）——**不得**用「结果近似」蒙过验收。
>
> 4. **成本边界（v2.6 写死，防止合计口径出现盲区）**：**2a = zip 解压全部条目 + `container.xml` / OPF（metadata / manifest / spine）解析，产出章节骨架**（架构文档口径 L1）；**2b = 各章 XHTML → 段落 / 图片页**（L2）。**2a + 2b 恰好覆盖 v2.4 原口径「单本解析」**——两者之外**不得再藏一段计时**，否则合计判定失效。
>
> **同一原则适用于候选 3（TXT）**：Rust **首版只做「探测出编码名」**，**解码仍留在 Dart**（保持既有 `charset` 与 `NF-C4`
> 六级兜底的行为不变）；若把解码一并交给 Rust，`encoding_rs` 与 Dart `charset` 在畸形样本上的差异同样会破坏 L2 等价性——
> **Rust 解码须另立阈值**。
>
> **拆分不改变负责人的决定**：档位 3 仍然包含 EPUB 解析，只是把一个原本**无法验收**的需求变成**可验收**的。
> **2b 属「首版暂不纳入（可条件纳回）」**，与下方**固化排除清单**（须走 `RUST-09` 的变更流程）**性质不同**，不得混为一谈。

**明确不上 Rust（固化清单，防止后续被误改；对应 `RUST-09`）**：

| 能力 | 不上 Rust 的理由 |
|---|---|
| **统计聚合** | ① 数据量小：4 万条会话 < 10MB JSON；② 既有指标 `NF-P8`（4 万条下首屏聚合 ≤ 500ms）**已达标**；③ §15.4 明确写过统计模块「零平台插件、五平台同一份代码」，上 Rust 会**作废这条结论** |
| **排版 / 分页计算** | 依赖 Flutter 的 `TextPainter`，**Rust 无法承担**（文本度量必须由 Flutter 引擎给出） |
| **书库索引读写、进度 / 书签 / 笔记持久化** | **IO 型负载**，非 CPU 密集；Rust 无收益，且会让「写入一律走原子写入」（`DATA-01`）出现第二套实现 |
| **AI / TTS / WebDAV 的网络层** | **IO 等待型**负载，瓶颈在网络与对端，Rust 无收益 |
| **简繁转换** | 查表替换，纯 Dart 足够（`P2-12`） |
| **图像处理（封面降采样、合成封面）** | 收益不小，但**本次不在档位 3 范围内**（负责人只批到档位 3）；列为后续可选评估项，**不得**借「顺手做」夹带 |

#### 15.6.3 引入门槛：先测后引 + 可验证阈值

**流程（每项候选能力都必须走完，不得跳步）**：

1. **先实现纯 Dart 基线**（基线本身就是交付物，且永久保留）；
2. 在目标机型（**Android 主力机**）上用**真实脏书样本**实测；
3. **只有超过下表阈值**才实施 Rust 版本；
4. 实测数据与结论**必须留档**（进入 §17「跨里程碑持续项」的性能基线）；**未超阈值的项，结论就是「不上 Rust」**，同样留档，避免下一轮重新讨论。

| # | 候选能力 | 触发阈值（**超过**才上 Rust） | 取值依据 |
|---|---|---|---|
| 1 | MOBI/AZW3 解压（PDB + KF6/KF8 + Huff/CDIC） | **打开 20MB AZW3 > 3s**，或**单本解压 + 解析 > 2s** | MOBI/AZW3 是「需解压后才能重排」的格式，用户预期接近「打开即读」；3s 对齐 `NF-P3`（50MB 大书 ≤ 10s）中「明显可感知」的档位。该项是本组唯一**确定性 CPU 密集**项，阈值有意设在易触发处，以体现其优先级 |
| 2a | EPUB 解压（zip 层） | **触发判定与 2b 合并计：单本「2a + 2b」> 800ms**（50MB 口径：合计 > 2s）。**分层值 400ms / 1s 仅作归因与优先级指引，不作为独立触发条件** | 由 v2.4 的「单本解析 > 800ms」**对半拆分**用于归因：解压（IO / 解压型）与正文抽取（字符串处理型）在 ZIP + DOM 链路上大体各占一半。**合计口径仍以 2026-09-18 决策文档的量级判断为据**（「单本解析在数十～数百毫秒量级、用户无感」）。**为什么不用独立触发（v2.6，架构师方案 A）**：2a = 300ms、2b = 450ms、合计 750ms < 800ms 时，独立口径会让 2b 单独触发——**独立触发把门槛拆松**。成本边界见 §15.6.2 处置 4 |
| 2b | XHTML → 段落（正文抽取层） | **与 2a 合并触发**（见 2a 行；分层值仅作归因）。**另有比阈值更严的前置条件**：必须先完成「切段规则规格化」（§15.6.2），**否则即使合计超过阈值也不得实施**——否则 `RUST-02` 的 L2 等价性无法验收 | 同上拆分口径（仅归因用）。该前置条件与阈值正交：**规格化解决「能不能等价」，阈值解决「值不值得更快」** |
| 3 | TXT 编码探测 + 分章 | **20MB TXT 分章 > 800ms** | `RD-02` 已要求「20MB TXT 能打开不闪退」，即单次分章需在打开体验内完成；800ms 约为 `NF-P2`（普通书 ≤ 2s）的 40%，为渲染与寻址留足余量 |
| 4 | 全书搜索（`CNT-06`） | **50MB 书全库搜索首屏结果 > 1.5s**，或**搜索期间出现单帧 > 16ms**（UI 卡顿） | 搜索是交互式能力，1.5s 是「键入后无感等待」的上限；帧时间阈值用于防止「不卡死但也不流畅」——`CNT-06` 只要求「不卡死」，本阈值更严 |
| 5 | RAG / BM25 索引构建（`AI-06`） | **单本 20MB 书索引构建 > 10s**，或**索引占用内存 > 原文的 1.5 倍** | 索引是**一次性后台任务**，10s 可接受（用户此时在读别的）；但内存倍率必须受限，否则直接违反 `NF-M1` / `NF-P2` |

> **⚠️ 阈值是「触发条件」而不是「验收目标」**：超过阈值只说明**可以**上 Rust，不等于**必须**上——还要一并评估工具链与维护成本（§15.6.5）。
> **分层阈值仅用于归因，触发判定以合计为准（v2.6 写死）**：候选 2a / 2b 各自的 400ms / 1s **不作为独立触发条件**；触发判定只看 **2a + 2b 合计**（单本 > 800ms / 50MB > 2s）。**反例**：2a = 300ms、2b = 450ms、合计 750ms < 800ms——独立口径下 2b 会单独触发，合计口径下**不上 Rust**；独立触发会把门槛拆松。
> **反向硬约束**：**未超过阈值的候选能力，不得实施 Rust 版本**（`RUST-06`）；否则 Rust 线会变成「凭感觉加代码」的口子。
> **顺序硬约束（v2.5 增补）**：**候选人 2b** 若未先完成「切段规则规格化」，**即使超过阈值也不得实施**（`RUST-06`）；

#### 15.6.4 对既有定案的推翻记录（必须留证）

**被推翻的文档**：`D:\Projects\567Reader\567Reader\.workbuddy\reports\epub-parser-dart-vs-rust-decision.md`

该文档的**明确结论是「EPUB 解析应继续用纯 Dart，不要引入 Rust」**，并给出 5 条判据：性能非瓶颈、Dart 生态足够、
工具链成本、调试可观测性、团队技能。它同时列出 **3 个「可以推翻我」的条件**，其中第 3 条为：

> 「**需要解析远超 EPUB 的格式（如 PDF 排版、复杂 CSS 级联计算）且要求极致性能**」

**本次即按该文档自己预留的第 3 条条件正式推翻它**，依据：

1. v2.0 之后项目范围已从「仅 EPUB」扩到 **PDF / CBZ / CBR / MOBI / AZW3 + 全书搜索 + RAG 索引**——正是「远超 EPUB 的格式」；
2. 其中 **MOBI/AZW3 的 Huff/CDIC 是位级解压算法**，本文档 §7.2 自己写着「**无 Dart 生态可借，需移植算法**」——属真正的 CPU 密集，与 EPUB 的 IO / 字符串型负载**性质不同**；
3. 该文档判据 3「工具链成本（决定性因素）」的**关键前提是「已拍板全平台（含 Web）」**；v2.4 已**放弃 Web**（§15.2），因此**不存在 Rust→WASM 编译链**，该决定性成本项已显著下降；
4. 该文档判据 3 还提到「引擎终态若改选 Rust 则协同」；本项目不以此为前提，但引入 Rust 后并不产生该文档所担心的「额外一套链」之外的代价（Web 已去）。
5. **Rust 侧存在现成的 Huff/CDIC 实现（v2.5 独立核实，这条进一步加固推翻依据）**：Rust 生态里**确实已有**成熟的纯 Rust 解压实现 —— **`mobi` 0.8.0（MIT）**，源码含 `src/compression/huff.rs`，其中 `load_huff`（解析 `HUFF` 魔数 + code dict + min/max codes）、`load_cdic_record`（解析 `CDIC` 魔数 + phrase dict）、`unpack`（位级滑窗解压）与 `pub fn decompress()` 均已实证存在。
   这意味着：该文档「**需要移植算法**」这一层顾虑——**在 Rust 侧不成立**；而它的判据 2「Dart 生态足够」**也未覆盖「Rust 侧更省事」这个角度**（它比较的是「Dart 有包 vs Rust 要自己写」，事实是**两边都有包**，只是 Rust 侧那份停更更久）。
   **但必须同时写明三条保留（不得省略）**：
   - ① **`mobi` 0.8.0 自 2022-12 起停更（≈3.9 年）**，无安全更新、无新特性 → 建议 **fork 到 `rust/vendor/mobi`**（MIT 允许自行维护），或 pin 死版本；由于 Rust 只在**只读链路**且 panic 已被兜住（`NF-D8`），**pin 是可接受的下限**；
   - ② **crate 的 README / 文档未声明支持 KF8 / AZW3 边界**：它只证实了 **MOBI6 + PalmDOC + Huff/CDIC + EXTH**；而 AZW3 是「MOBI6 头 + KF8 记录」的**双格式**，crate 能否处理 KF8 boundary、能否读出 KF8 章节列表**未证实** → **必须做一次最小验证**，且安排在实施早期（避免到 MOBI 正式落地时才发现）。**KF8 入口判据（v2.6 补录）**：合法 KF8 有两种入口——`mobiHeader.version >= 8` 直入，或 KF6 的 EXTH boundary 记录号跳转重读头（失败回落 KF6）；**最小验证就拿这两类文件各测一次**；
   - ③ 源码残留 `println!` / `eprintln!` 调试输出（`unpack` 内有 `println!("max_code...")` 与 `eprintln!("{:#?}")`）→ **必须 patch 掉**，否则 release 日志刷屏 + 性能损失；这是 fork 的必然工作。
6. **Dart 侧的最短路径（v2.6 补录调研事实，负责人已确认）**：「无 Dart 生态可借，需移植算法」对 **Dart 包生态**成立，但 567Reader 有一套**可直译的纯 Kotlin 参考实现**——`app/src/main/java/**/lib/mobi/`（33 文件约 1600 行：PDB 容器 / KF6 连续 HTML 流窗口 / KF8 SKEL+FRAG+FDST+INDX / Plain·LZ77·HUFF-CDIC 三解压器）。纯 Dart 原型基线（§17 M3.5 T02 / M2b `FMT-04`）**不必从规范从零手写**，直译 Kotlin 实现即可；其 HTML 清洗层**不直译**，保持 Dart（与候选 2b 同一模式）。
   **并且必须显式写明这条分支（不许含糊）**：**若最小验证证明该 crate 处理不了 KF8**，则退化为「**用 crate 的 HUFF/CDIC + 从 Kotlin 参考实现直译 KF8 boundary / SKEL/FRAG 拼段**」（比按规范自写便宜一个量级，见本节第 6 条）——此时**移植工作量不再从零回来，但仍需独立工时**，**阈值 1（打开 20MB AZW3 > 3s）的取值需重新与项目负责人讨论**（见 §16 `Q25`）。**不得**在未验证前假设 KF8 可直接用。

**同时必须写明（不得省略）**：该文档关于 **EPUB 解析**的判据**并未被推翻**——

> 「EPUB 解析的负载是『解压 + XML/DOM 字符串处理』，属 IO/字符串型、非 CPU 密集；单本 2–50MB，

**条件性说明（重要）**：本批**可以整体不做**。若 §15.6.3 的阈值全部未被超过，则 M3.5 的结论就是「不上 Rust」——
**这同样是一份合格交付**（并留档）。
