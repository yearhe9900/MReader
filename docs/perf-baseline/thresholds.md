## 3. 口径缺陷与「无条件下界」（**本批新发现，必须读**）

### 3.1 问题：无目录书的「2a + 2b」是**重复计数**，不是中性重叠

§15.6.2 处置 4 把成本边界写死为「2a = zip + container/OPF → 章节骨架」「2b = 各章 XHTML → 段落」，
并声明「2a + 2b 恰好覆盖原口径」。**本批实测发现该边界在「无目录书」上不成立**：

本工程的 EPUB 解析在 `toc` 为空时于 `load()` 内做 `flatTitles` **标题预取**
（逐章解压 + XHTML 解析，性质属 2b，M2a-T06b `56fabe5`）。因此

```
无目录样本：2a（= load + chapters） ≈ 真 2a + F      （F = flatTitles 预取）
            2b（= 全书 content）    = 真 2b
            合计                    ≈ 真合计 + F     ← F 被算了两次 ⇒ 高估
```

**实测坐实**（同口径、同一台机器、同一轮）：

| 样本 | 有目录 | 2a | 说明 |
|---|---|---|---|
| 王晋康作品选（真实脏书） | ✓ | **48ms** | 走目录分支，**不触发** `flatTitles` → 这是**干净的真 2a** |
| `big_320.epub` | ✗ | 84ms | 无目录但章体积极小 |
| `big_bodies.epub` | ✗ | **7608ms** | 无目录 + 100 章 × 1.4MB XHTML → 7608ms 只可能是逐章 XHTML 解析 |

「真 2a = zip + OPF 产出骨架」在同一个解析器上不可能从 48ms 跳到 7608ms（**差 158 倍**）。
→ 之前的说法「**合计不受影响，同一份工作只算一次**」**是错的**，本批予以更正。

### 3.2 处置：给判定的同时给**无条件下界**

因为 2b 的测量**只计 `content(i)` 循环**（`chapters()` 已在外层调用并被缓存），它**等于真 2b**；
又因真 2a ≥ 0，故

```
真合计 = 真 2a + 真 2b ≥ 真 2b = 2b 分层值        ← 无条件下界
```

harness 在每条合计记录里同时给「上界（分层和，判定口径）」与「下界」，并据此区分两种 over：

- **下界自身已越死区** → 结论写「**over 与口径无关**」——无论 `flatTitles` 算进 2a 还是 2b，
  合计都必然越阈值（**本批真实脏书即属此类**：下界 1322ms > 880ms）；
- **仅上界越死区** → 结论写「**over 依赖上界口径**，必须补一个有目录大样本复核后才可据此开工」
  （`RUST-06` 的开工纪律；本批 `big_bodies` 属此类，但它的 2b 本身 7536ms 也已单独越线）。

## 4. 结论：给 T03 gate / T04 的三个输入（**建议负责人拍板**）

### 4.1 阈值 2 判 `over`，但「**能上 Rust 的 2a**」本身没有超标

这是本批最重要的、也是**规格层面的一个张力**，如实登记供 gate 拍板：

- 阈值 2 的触发口径（v2.6 方案 A）是 **2a + 2b 合计**，目的是防「独立触发把门槛拆松」；
- 但**首版 Rust 只替换 2a（解压层 L1）**——2b 首版明确不纳入（`§15.6.2`：Dart `package:html`
  的切段行为是其特定实现的隐式行为，Rust 几乎不可能逐字节复现 → `RUST-02` 的 L2 等价性无法验收）；
- 实测：有目录真书合计 **1370ms**，其中 **2b = 1322ms（96.5%）、2a = 48ms（3.5%）**；
  `big_320` 合计 157ms（2a 84 / 2b 73）；无目录 `big_bodies` 的真 2a 亦在百 ms 量级。

→ **按合计判 over 可以授权实施 Rust，但可实施的那一层（2a）实测只有几十 ms**。
真要把 1370ms 降到目标，必须动 2b；而 2b 既不在首版范围、又缺「切段规则规格化」前置条件。
**建议**：gate 拍板时把「2a 单独的最大实测值（84ms，未越 400ms 归因线 5 倍）」一并纳入评估——
即「阈值 2 over」这一条是否足以支撑 T04 开工，需要负责人在知道**收益只有几十 ms**的前提下决定。

### 4.2 阈值 4 判 `over`，但根因有**纯 Dart 优化路径**（先优化再重测，比上 Rust 更划算）

超标 5.08× 的只有**无 toc 大书**，根因已定位（`search.md` §2）：`flatTitles` 全书预解压，
且**每次搜索都要吃一遍**（搜索走后台重建路径，阅读页的解析缓存含闭包不可序列化）。
挂账 #6 的三个纯 Dart 优化候选：**a 已于 2026-10-06 实施**（搜索路径
`prefetchFlatTitles: false` 跳过预取，`search.md` §6、`tech-usage.md` §2.66）；
b 被 a 取代；c（有目录真书复测）**仍待真机复跑**。

→ `RUST-06` 只要求「**超过阈值才允许**上 Rust」，**不要求「超过就必须上」**。
建议顺序：**先做纯 Dart 优化 → 重测 → 仍超标再考虑 Rust**；否则是在为一段本可省掉的
工作引入 FFI 复杂度与 `RUST-02` 等价性验收面。

### 4.3 阈值 3 判 `borderline`，且**前置条件把首版范围压得很窄**

阈值 3 桌面上 1.03×（821ms）——**已在 10% 死区内**。但其前置条件写死：「首版只做
『探测出编码名』，**解码仍留 Dart**」（保持既有 charset 与 `NF-C4` 六级兜底行为不变）。
20MB TXT 的成本主体是**全量解码 + 分章**，只把「探测编码名」搬去 Rust 拿不到多少收益。
→ 本项应在真机复测后再定，且判定时要连同前置条件一起读。
