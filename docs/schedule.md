## 0. 排期假设（先看这节，否则后面的数字无法解读）

### 0.1 投入档位与工时换算

| 项 | 取值 | 说明 |
|---|---|---|
| 投入档位 | **单人 · 业余投入** | 全部批次串行推进为主（见 §0.4） |

| **名义工时** | **20.5 h/周** | — |

### 0.2 为什么「1 人天 = 5 净推进小时」而不是 8

- 全职口径下，一个 8 小时工作日的**净编码时间**行业经验值就是 5–6 h（会议、沟通、构建、上下文切换占掉其余）；
- 本项目是**业余投入**，若把「1 人天」定义为 8 名义小时，会与「一个晚上干 2.5 小时」的直觉严重冲突，导致估算失真；
- 因此本文**统一以「净推进小时」为底层单位**，再用 `1 人天 = 5 净推进小时` 换算成人天，使其仍可与全职口径对照：
  - **1 个典型工作日晚上（2.5 h 名义）≈ 1.9 h 有效 ≈ 0.37 人天**；
  - **1 个典型周末（8 h 名义）≈ 6 h 有效 ≈ 1.2 人天**；
  - **1 周 ≈ 3 人天**（工作日 1.85 + 周末 1.2）。
- 反过来读：**一个 4 人天的任务 = 20 净小时 ≈ 7 个晚上 + 半个周末 ≈ 1.3 周**。请按这个体感读下面所有数字。

### 0.3 缓冲怎么放（不玩双重缓冲）

- **各任务人天中已含 10%–20% 的调试 / 回归 / 返工余量**，因此**不再**在每个任务上单列缓冲百分比；
- 项目级不确定性改为**在日历里显式预留**：节假日折损 + 意外零产能周，合计 **4.5 周**（见 §0.5）；
- §5 的每条风险另有**独立的应对工时**（计入对应批次人天或明确标为「额外」）。

### 0.4 单人串行为主的三条硬约束

1. **同一时间只推一条主线**。单人业余下「并行」的真实收益极低——两条线各自留着半截上下文，切换成本会吃掉全部收益（见 §4）。
2. **大任务必须切成「一两个晚上能收尾」的粒度**。本文任务粒度原则：**单任务 ≤ 5 人天（≈ 2 周）**；> 4 人天的任务在开工前**必须再切一次**，否则极易变成「两周没碰、回来全忘」的长尾任务。
3. **每批结束时必须有一个可交付版本**（PRD §17 原则保留）。批次内的任务可以留尾，但批次出口必须绿。

## 4. 并行机会

### 4.1 单人业余下**真正可利用**的并行（只有两条）

| # | 可并行的两件事 | 为什么真能并行 | 怎么排 |
|---|---|---|---|
| **P-1** | **M3 主线（AI/TTS） vs 支线（统计页 `STAT-03~07`）** | PRD §17 原文：文件**零重叠**；且心智模式互补——AI/TTS 是「网络 + 流式 + 平台集成」，统计页是「本地聚合 + `CustomPainter` 自绘」 | **周末整块时间 → 主线**（需要连续调试真机）；**工作日晚上 → 支线**（自绘图表天然可切片，一个晚上画一根柱子也能收尾） |
| **P-2** | **M2b-T08（`STAT-01/02` 采集内核） vs M2b 的 `FMT-*` 格式扩展** | PRD §17 原文：「只有数据层、没有任何 UI，与格式扩展/检索不共享文件，可并行推进」 | 格式扩展（PDF/CBZ）需要连续时间 → 放周末；采集内核可切片 → 放工作日晚上 |

> **这两条的收益是「换脑子 + 减少空窗」，不是「缩短工期」**。本文的周数估算**没有**依赖并行收益。

### 4.2 看起来能并行、其实**不能**（不要尝试）

| # | 看起来能并行 | 为什么不能 |
|---|---|---|
| **N-1** | M1 内部各模块（书库 / 阅读页 / 元数据 / 排版） | 它们**共享同一批正在新建的基础文件**（存储、抽象、路由、主题）。单人下并行 = 两处各写一半、接口对不上，返工成本 > 收益 |
| **N-2** | M2a 与 M2b | `FMT-01`(PDF) 与 `FMT-02`(CBZ) 都依赖 `M2a-T01` 的图片渲染与容器宽度自适应能力，是**强依赖**不是并行 |
| **N-3** | M3 的 AI 与 TTS | 两者都消费「段落切分 + 选中态 + 定位跳转」：`TTS-02` 高亮与 `AI-02` 划词共用同一套段落定位设施。并行会做出两套 → **必须串行（先 AI 划词，TTS 复用）** |
| **N-4** | M3.5 与 M4 | PRD §17 明确要求 M3.5 在 M4 **之前**：同时引入新构建链（Cargokit / FRB）会把「发布验收」与「工具链风险」叠加，一旦构建不稳会同时阻塞 M4 全部验收项 |
| **N-5** | 写业务代码 与 调玻璃态视觉 | 视觉调优需要反复看效果，与逻辑调试的心智模式冲突；更关键的是**本机 Windows 只有 Skia 轻量路径（`Q3`）**，本机调出来的观感与 Android（主力机）不一致 → 视觉调优必须集中在一个窗口内、在 Android 真机上做，不能碎片化 |
| **N-6** | M3.5 的 T01/T02 与 M4 的 `SYNC-01` | 技术上零重叠，但两者都在定义跨模块的架构契约，单人下同时开两条「架构级」线索会互相污染 → **不做** |

### 7.3 重排触发规则（写死，避免「慢慢滑走」）

| 触发条件 | 动作 |
|---|---|
| **单批累计偏差 > 20%** 或 **> 3 人天**（取先到者） | **必须**重排后续所有批次的周序，并回填 §6 |
| **连续 2 周进度 < 计划的 50%** | 触发「任务再切分」或「裁剪评审」（见 §6.4） |
| **低置信度任务（标【低】）的实际偏差 > 50%** | 复核同类未开工任务的估算，整体修正 |
| **gate（M35-T03）结论翻转** | 切换时间线（A ↔ B），重排 §6，并回写 PRD §17 M3.5 / M4 的工期 |
| **总工期预测偏差 > 4 周** | 重排 §6 日历，并**同步更新 PRD §17 中对应里程碑的周序**（两份文档必须一致） |
| **需求编号增删或优先级调整** | 重算受影响批次的人天；**PRD §6 与 §17 先改，本文档后改** |

### 7.4 与 PRD 的同步约定

- **PRD §17 是「做什么 + 做到什么算交付」的唯一出处**，本文档是「多久 + 什么顺序」的唯一出处；
- 任一里程碑的**范围**变更 → **先改 PRD §17**，再改本文档；
- 任一里程碑的**工期**变更 → **先改本文档 §6**，再把新周序回写 PRD §17 的「工期估算」行；
- 两份文档中同一里程碑的**周序 / 人天数字必须一致**，不一致即视为缺陷；
- **需求编号不得重编**；删除的需求保留编号空位（PRD §6 既有约定，本文档同样遵守）。

## 8. 项目负责人必须先看的两个决策点

### 决策点 1：iOS / macOS（P1）怎么验？—— **必须在 W12 末（2026-12-13）前决定**

本机是 Windows，**iOS / macOS 无法在本机构建，更无法真机验证**。这不是「以后再说」的问题，而是会影响
M4-T08 的排法与最终对外口径（§15.3 红线：**不得宣称五平台功能等价**）。

| 方案 | 做法 | 成本 | 后果 |
|---|---|---|---|
| **A（推荐）** | M4 收尾期安排一次**集中适配窗口**：借 / 租一台 Mac 或用云 Mac 服务（如 MacStadium），3–5 人天集中处理 iOS / macOS 构建 + 核心阅读真机验证 | +3 ~ 5 人天（≈ 1.5 周） | 五平台名副其实；但需要**提前预约资源** |
| **B** | 本期只交付 **Android + Windows**（P0 已达标），iOS / macOS 在文档与 UI 上**诚实标注**为「构建未验证 / 未做真机验证」 | 0 | 符合 §15.3 诚实降级原则；P1 平台承诺打折 |
| **C** | 找有 Mac 的人代为验证（出一份验证清单） | +1 ~ 2 人天（沟通） | 质量取决于对方配合度；沟通成本不可控 |

> **为什么必须在 W12 末前决定**：方案 A 需要提前约资源（机器 / 人 / 服务），临时找会拖到 M4 尾期；
> 若到时拿不到资源而临时改 B，会同时影响 `TTS-03`（iOS 后台播放，§15.3 列为「需验证」）与 `P2-08`（iOS Document Types）的排法。

### 决策点 2：M3.5 的准入口径 —— 「只验构建通路」还是「完整走完先测后引」？—— **需在 W43 末（2027-07-18）前确认**

| 方案 | 做法 | 人天 | 说明 |
|---|---|---|---|
| **A（本文默认 · 时间线 A/B 共用）** | 完整走 `RUST-06` 的「先测后引」：T01 → T02（六项候选基线实测留档）→ T03（构建通路 gate）→ 按结论决定是否 T04/T05 | 12（不上）/ 28（上） | 符合 `RUST-06` ④「未超阈值的结论同样留档」，下一轮不必重新讨论 |
| **B（压缩）** | 只做 T01 + T03（最小构建通路验证 + 结论），不做完整基线测量 | ≈ 7 | 省 ≈ 1.5–4 周，但留下「没测过就说不做」的口子；**不推荐** |
| **C（整体跳过）** | M3.5 完全不做 | 0 | 省 4–10 周；但 `Q19` / 架构 §L9 建议「至少做一次可行性验证」，且 `RUST-07`/`RUST-08`（约束性条目）会失去落地载体 |

> **推荐 A**。理由：M3.5 是唯一一个「**不做也是合格交付**」的批次，它的价值主要在于**留档结论**——
> 花 12 人天把「六项候选的实测数据 + 不上 Rust 的理由」固化下来，可以让下一轮不必再从零讨论（PRD §15.6.4 的留证原则同源）。
